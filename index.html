The Results - What Breaks

Common Failure Patterns When Comparing to Reference:

1. Missing zero-value rows (all models)

  • Reference data includes candidates with 0 votes
  • LLMs consistently omit these
  • San Saba County, TX: 6 write-in rows with 0 votes in reference, all missing
  • Panola County, TX: 6 minor party candidates with 0 votes, missing

2. Incomplete extraction (especially Claude models)

  • Reference has 3,936 rows
  • LLMs extracted only 3,131-3,697 rows
  • Missing Supreme Court races in Jones, Lynn, Cottle counties

3. Vote count errors (PDF-specific)

  • Panola County, TX: Claude Haiku 16.2% match to reference (233→227)
  • Jones County, TX: <14% match across multiple models
  • Same counties fail across different models

4. Precinct name OCR errors (all models)

  • Mississippi: 2,898 precinct name errors vs. reference (Claude Haiku, 80 counties)
  • Texas: 0 precinct errors across 2,495 verified votes
  • Fixable with validation scripts
Key insight: When models disagree with reference data, the same problem counties appear consistently. This isn't random—it's tied to PDF characteristics we haven't fully identified.

Pennsylvania - What Custom Parsers Actually Cost

Baseline Method: Custom Python Parsers

Electionware system (used by many PA counties):

  • Months of development, debugging, testing
  • Documented 10 major issues encountered during development
  • Result: High-quality, reliable extraction... eventually

Issues discovered building the reference parsers:

  • Hard-coded values → dynamic extraction (weeks of refactoring)
  • Format variations between election years (2024 vs 2025 broke parsers)
  • Missing party codes (DAR = cross-filing)
  • Loop control bugs (candidates misattributed to wrong offices)
  • Office header variations (ALL-CAPS vs. Mixed-Case)
The parser works great now. But:
  • Required Python expertise
  • Broke when format changed slightly
  • Not portable to other states
  • Substantial upfront time investment
  • Ongoing maintenance for format changes

LLM comparison: Parsers = high accuracy, high development cost. LLMs = variable accuracy, zero development cost.

Real question: If we're comparing LLMs to "verified reference data," what if the LLMs could have created that reference data faster?

Verification Strategies

You can't just trust LLM output. Here's how we validate against reference:

1. Direct comparison to reference data

  • Vote count matching (what we measured)
  • Precinct name validation
  • Candidate presence verification
  • Identifies systematic vs. random errors

2. County-level total checks

  • Extract precinct data with LLM
  • Compare sums to official county totals
  • Catches missing races, incorrect vote counts
  • Independent of reference data method

3. Multi-model extraction on samples

  • Run 2-3 models on representative counties
  • Where they agree, confidence is high
  • Where they disagree, compare to reference

4. Automated validation patterns

  • Row count checks (expected vs. actual)
  • Zero-vote pattern detection
  • Race completeness verification

5. Targeted manual review

  • Focus on counties with low match rates (<80%)
  • Spot-check high-confidence extractions (>95%)
  • Verify error patterns found in samples
Key point: Having reference data let us measure accuracy. In production, you'd use methods 2-5.

Real-World Deployment Recommendation

Production Strategy Based on Comparison to Reference:

Tier 1: Replace existing extraction methods (95%+ match)

  • PDFs like Limestone, Scurry, San Saba (TX)
  • Adams, Amite, Attala (MS with Gemini Flash/2.5 Pro)
  • Use LLMs instead of OCR + manual cleanup
  • Validate with county totals

Tier 2: LLM as first pass (70-90% match)

  • Most TX/MS sample counties
  • Faster than manual, but needs verification
  • Multi-model extraction for critical races
  • Systematic spot-checking

Tier 3: Stick with custom parsers or manual (<70% match)

  • PDFs like Panola, Jones, Pike (consistent <20% match)
  • Format changes frequently (PA Electionware between years)
  • Critical accuracy requirements
  • Or: use LLMs with heavy manual verification
The value proposition:
  • Good formats: LLMs can replace weeks of OCR + manual work
  • Medium formats: LLMs reduce manual work significantly
  • Bad formats: LLMs waste time, stick with proven methods

What This Actually Means

What we learned comparing to verified data:

  • Some PDF formats: LLMs match months of manual work (99-100%)
  • Other formats: LLMs can't match manual work (<20%)
  • Zero-value rows universally problematic across all models
  • Format matters more than model sophistication

Cost-benefit analysis:

  • Mississippi OCR + manual: weeks of work per county
  • LLM extraction: minutes per county
  • If accuracy matches: massive time savings
  • If accuracy doesn't match: wasted effort
The sampling approach:
  • Test LLMs on 3-5% of your counties
  • Compare to reference data (or build reference from LLMs + validation)
  • Identify which formats work well
  • Scale up on similar formats, use traditional methods on others

What we can't do yet:

  • Predict which PDFs will work without testing
  • Eliminate verification step
  • Handle zero-vote rows reliably

The real value: For formats that work, LLMs can produce reference-quality data in a fraction of the time. For formats that don't work, they tell you quickly—fail fast, fall back to proven methods.

Next steps: Understanding what makes Limestone different from Panola. Better prompting for zero-value rows. Hybrid approaches.
